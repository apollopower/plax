## Clusters and phases

### Phase 1 — Quick wins, zero architectural risk

**Issues:** #46, #49, #50

- **#46 `discoverRoot`** — 1-file fix in `cmd/plax/main.go:763`.
  Use `git rev-parse --git-common-dir` to find the real repo root,
  bypassing worktree-local `plax.json` files. Blocked by nothing.

- **#49 Worktree traversal** — `plax init` warns about tooling configs
  that glob from root; auto-add `.plax/` to gitignore; document required
  ignore entries covering VCS, test runners, linters, and type checkers.
  No layout change needed — the priority is making the problem visible
  and giving the user explicit ignore entries to add.

- **#50 Direction-blind advice** — `schemaDrift` in
  `pkg/status/status.go:281` already computes both the provenance hash
  and the worktree migration set. Branch the drift message into three
  cases: (a) branch migrations ahead of base → re-migrate; (b) base ahead
  of branch → rebase or rebuild base; (c) both diverge → rebuild from
  matching base. Also name the specific migrations involved in each
  direction.

### Phase 2 — Health plumbing

**Issues:** #51, #52

- **#51 Cached health** — `healthDrift` at `status.go:218` reads
  `rec.Health` verbatim — a passive field written once at `up`/`resume`
  time and never refreshed. Change `ls` and `status` to run live
  `process-liveness` and `tcp-reachability` checks rather than serving
  the stale cached value. Reuses existing `pkg/verify` check functions.

- **#52 Process ports unprobed** — `CheckServices` in `pkg/verify`
  builds the endpoint set from `deps.Blueprint.Services` only. Extend to
  include allocated process ports from the registry's per-instance port
  map. Add a bounded poll-with-deadline so the app has time to listen
  before the check samples.

**Design decision — async settle (not blocking `up`):** `up` already
returns in ~1.3 seconds on a real project, while the application may
take ~20 seconds to first answer HTTP. Making `up` block on readiness
would trade the tool's defining speed property for correctness that is
better served by a live-polling async model. The approach:

1. `up` runs static checks (env, template) before returning — these are
   genuinely immediate and catch misconfiguration.
2. Runtime checks (process-liveness, tcp-reachability of both service
   and process ports) run asynchronously on a bounded poll loop, writing
   health to the registry once they settle.
3. `ls` and `status` always run live checks — they are the "what's
   actually happening" commands, the user explicitly asked.
4. If this proves too unreliable (users ignore stale health), the
   fallback is a `--wait` flag on `up` that gates return on readiness,
   preserving fast path by default.

### Phase 3 — Schema drift overhaul

**Issues:** #47

- **#47 Drift never clears** — `schemaDrift` in `status.go:281` compares
  `prov.SchemaHash` (a hash of migration filenames stamped at clone time,
  frozen forever) against `worktree.SchemaFilesAtRef(...)` (a hash of
  migrations at the worktree's current HEAD). Migrating an instance
  inside the worktree never updates the provenance stamp, so the left
  side is immutable and drift never resolves.

  Fix: read applied-migration identifiers directly from the instance's
  database at status time and compare that live set against the files at
  worktree HEAD. This removes the stamp from the comparison entirely and
  is correct by construction. Requires a blueprint field for the
  applied-migrations table name.

  ⚠ Fixing this also gives #50 the per-migration direction data for free
  — the live query returns the exact set of migrations applied, making
  the "database has X migrations worktree does not declare" message
  trivially computable.

### Phase 4 — Isolation hardening

**Issues:** #48, #53

- **#53 Scratch directory** — Create `scratch/` inside each instance
  worktree at `up` time. Add the directory to `.git/info/exclude` for
  that worktree (per-worktree, not committed to the repo). Remove on
  `down`. Report its existence in the `up` summary alongside the
  worktree, branch, databases, ports, and logs. This is a small,
  self-contained addition with no cross-cutting concerns.

- **#48 Shared `node_modules`** — The hardest remaining issue. Four
  design options, ordered by cost:

  1. **Detection-only.** Add a verification check that compares the
     branch's dependency manifest and lockfile against the base's. When
     they differ and the tree is shared, fail loudly with a message
     naming the specific files. Does not fix the gap but converts a
     silent wrong answer into a visible one — which is the property that
     matters most for correctness.

  2. **Hardlink copy at `up`.** Hardlink the parent's dependency tree
     into the worktree at `up` time (near-zero cost). Re-run install only
     when the branch's manifest/lockfile differs. Preserves the
     "instances are cheap" property while restoring isolation.

  3. **Blueprint-declarable strategy.** Add a `dependency` block to the
     blueprint that names directories and a strategy
     (`share` / `copy` / `install`). Repos opt into expensive-but-correct
     where it matters.

  4. **Per-instance install.** Full install per instance. Correct but
     pays full cost and disk per instance, working against the speed
     property that makes the tool pleasant.

  **Recommendation:** Start with (1) — the detection check — which can
  ship in Phase 1 alongside the other quick wins. It prevents the worst
  failure mode (confidently reviewing a dependency change against the
  wrong tree). The hardlink approach (2) is the likely sweet spot for a
  fuller fix, to be evaluated in a dedicated implementation plan.

### Phase 5 — Docs and polish

**Issues:** #54

Extract actionable items from the feedback issue:

- [ ] Document the cloned database as an investigation surface in the
  manual (`docs/manual.md`). Make its reachability obvious in the `up`
  summary output (add a `database: plax_i1 (psql -d plax_i1)` line to
  the existing summary block).
- [ ] Document the statistical-accuracy limit — plan-dependent,
  volume-dependent, and statistics-dependent queries must be diagnosed
  against production, not the instance. The instance is structurally
  accurate but statistically naive.
- [ ] Consider running `ANALYZE` on the cloned database after `up`, or
  offering it as a flag (`--analyze`). This would not close the gap but
  removes the most surprising instance of it (the zero-statistics case).
- [ ] State the read-vs-write rule explicitly: isolation earns its cost
  when agents write. For read-only fan-out it is pure overhead. "One
  instance per agent" is the wrong heuristic; "one instance per mutator"
  is closer.
- [ ] Evaluate the mailbox design note — direct agent-to-agent handoff
  propagates errors as efficiently as findings. The hub (user) is the
  right router for high-stakes claims that need adjudicating against
  ground truth agents cannot reach.
