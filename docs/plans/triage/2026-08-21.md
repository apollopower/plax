## Clusters and phases

### Phase 1 — Onboarding, human-facing: #64

**Issue:** #64 — Getting Started / Installation in the manual.

The cheapest, highest-confidence win. `docs/manual.md` already has a §2
Installation section and a §3 First setup, but no end-to-end "from zero to a
running instance" walkthrough. Phases 1–18 shipped a large surface; the
manual likely carries stale references to pre-ship behavior.

Scope:

- Add a "Getting Started" walkthrough: install → `plax init` → inspect
  `plax.json` → `plax up i1` → attach / exec → down. One continuous narrative
  a first-time user follows start to finish.
- Audit `docs/manual.md` and the README for references that no longer match
  post-phase-18 behavior. The `plax verify`, `plax status` live-health, and
  schema-drift behavior from plans 15–17 are the likely drift points.
- Low risk: docs only, no runtime surface.

### Phase 2 — Agent-facing on-ramp: #66 (re-frame)

**Issue:** #66 — Cookbook. **Decision pending; reframed during triage.**

The original framing ("print ready-to-use shell snippets per agent runner")
is a UI for docs — it conflicts with the project value that plax "ships no
UI" and "composes with other tools." A plain `plax cookbook claude-code`
subcommand printing snippets is a documentation feature wearing a command's
costume, and a recipes page in the manual would serve the same humans
equally well. That is the argument for treating #66 as a doc section.

**The maintainer has reframed it, and the reframe is stronger.** The real
need is not human-facing snippets — it is an **agent-facing on-ramp**: a way
for a coding agent to call plax over the CLI and get the context it needs to
use plax correctly for its own purposes and dev environment. Agents cannot
navigate a manual; they interact through the CLI. Concretely that means plax
should be able to explain itself on demand — its available commands, the
blueprint contract, the lifecycle, what `attach`/`exec`/`rederive` do, how to
acquire an isolated environment — in a form an agent consumes directly.

This is squarely within scope: plax provisions environments **for coding
agents**. An agent-facing self-describing interface is not orchestrating
agents; it is making the existing environment-management contract legible to
its primary consumer. The "ships no UI" value is about not owning windows and
panes, not about refusing to answer `plax --help`-style queries with real
substance.

Decisions (resolved 2026-08-21):

- **Vehicle:** `plax help` — a single comprehensive markdown document bundled
  into the binary. One entry point, no discovery bootstrap. Markdown is the
  pragmatic format: LLMs parse it natively, humans read it in the terminal.
  No subcommand tree (`plax explain <topic>`) and no JSON output for this
  iteration.
- **Scope:** Full operational semantics — lifecycle states, drift model,
  verification, and `send`/`recv` IPC. An agent with partial knowledge is
  worse than one with none; give it everything it needs in one document.
- **Dynamic vs. static:** Static. A fixed document compiled into the binary,
  versioned with it, always correct, offline-capable. No runtime coupling to
  the repo's `plax.json`.

### Phase 3 — Tooling polish: #65

**Issue:** #65 — `plax upgrade` self-update.

Self-contained and reasonable, but the least aligned with the core mission
(managing environments). It is tooling hygiene, not capability. Moderate
effort concentrated in the edge cases: detecting the install method
(Homebrew vs. direct binary vs. `go install`) and doing the right update per
method, plus a GitHub Releases lookup for the direct-binary path.

Scope notes:

- If a repo installs plax via Homebrew, the correct behavior may be "run
  `brew upgrade plax`", not a self-replace. Detection must be honest about
  when it can and cannot self-update.
- Direct-binary replacement must be atomic (write temp, rename) and handle
  running-from-the-binary-being-replaced (use `/proc/self/exe` on Linux).
- **Recommendation:** sequence after #64 and the #66 decision. Nothing about
  #65 is time-sensitive; it should not preempt the on-ramp work.

### Phase 4 — Core capability: #67 (design-first)

**Issue:** #67 — Instance pooling via `plax pool`.

The only issue that touches core lifecycle, drift, and the registry — the
most fragile surface in the codebase. Highest value (removes `up` latency
from the agent's critical path, which is the exact latency the #66 on-ramp
agents will feel), but also the highest risk and the most speculative: pooling
is a latency optimization whose payoff can only be confirmed once the
cost of `up` is measured in the field.

The issue's own design is already strong and stays on-mission:

- **Drift.** Pooled instances' blueprint stamp goes stale on `plax.json`
  change; `acquire` is the single decision point — rederive or reject.
- **Registry.** Pool state lives in `.plax/registry.json`; pooled instances
  are just suspended instances with a `pooled` flag. No new state store.
- **No daemon.** Passive state; no background process watching for drift.
  `acquire` blocks only when the pool is empty (optional timeout).
- **Single-consumer.** `acquire` is the only admission point.

Scope risk to contain: #67 sits at the edge of the "does not orchestrate
agents" line. A pool that agents drain and refill is environment management;
a pool that *schedules* which agent gets which instance is orchestration.
The `acquire` blocking model already nudges toward the former. Keep it there.

**Recommendation:** write this as a full 9-section implementation plan
(`docs/plans/19-pooling.md`) *before* any code, per the plan-file
conventions. The registry-flag, drift-on-acquire, and blocking-`acquire`
semantics all deserve the plan's edge-case (`⚠`) discipline before touching
`pkg/instance` and `pkg/registry`. Sequence after #64 and the #66 decision so
the plan can reuse the on-ramp's sense of how agents actually acquire
instances.
