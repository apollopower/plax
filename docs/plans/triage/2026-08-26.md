## Clusters and phases

### Phase 1 — Core lifecycle: #75 (migrations on `up`) — P1

**Issue:** #75 — `plax up` should apply pending migrations, with `--skip`.

This is the remediation half of the drift loop the project already opened.
#47/#50 (plans 16/17) made drift *detectable* and made the advice
*direction-aware*; `status` has told users "re-migrate the instance" since
then. #75 makes new instances come pre-migrated so the advice is never
needed for them. The cost it removes is not the 6 seconds of migrating —
it is the detour and the standing risk that a stale-base schema gets read
as a regression in the branch under test. That failure was observed twice
in one day; it is every instance created after the base drifts.

The proposal is well-formed and matches the project's conventions:

- **Run `seed.migrate` as an `up` phase.** Insert it after the database
  clones (Step 5 in `pkg/instance/up.go`) and before workloads start, so
  processes boot against the final schema and the verify phase's
  schema-drift check sees the migrated set. The existing "clone →
  migrate → seed" order in `base refresh` is the precedent.
- **`--skip migrate[,verify,...]`.** A general named-step skip beats a
  per-step boolean flag; unknown names are a hard error, not a silent
  no-op. `migrate` and `verify` are the two named steps worth supporting
  from day one; `seed` stays base-only.
- **Report the step.** `applying migrations...` in the `up` output, the
  way service startup already is.
- **Fail loudly.** Per the #52 lesson ("all checks passed" preceded
  readiness): a migrate failure fails `up` with rollback, never leaves a
  half-configured instance recorded as healthy.

**⚠ The existing migrate plumbing cannot be reused.** `BaseManager.
runMigrate` → `runCommand` is base-oriented: it runs in the *base repo
workdir* and overrides only `DATABASE_URL` (from the base DSN). Pointing
it at an instance would migrate the wrong database and miss every other
derived variable (`DATABASE_TEST_URL`, multi-DB vars, rendered `{{VAR}}`
values). The new phase must run the migrate command in the *instance
worktree* with the *instance's derived env* — the same plumbing
`process.Spawn` uses (`env.Render` + derived `.env` + workdir), not
`runCommand`. This is the main implementation risk and deserves the plan's
`⚠` discipline.

**Count reporting needs `applied_migrations`.** "10 applied" can only be
computed as a live-set diff when `seed.applied_migrations` is configured
(plan 17 machinery). Without it, report the step without a count — the
step itself is still correct and a no-op when the base is current. The
author's own config gap is real and confirmed here: `applied_migrations`
is `omitempty`, and neither `plax init` scaffolds it nor `doctor` warns
when it is absent. Worth a follow-up issue (see below); it does not block
this work, as the issue itself argues.

**Scope:** `pkg/instance/up.go` (one new phase), `cmd/plax/main.go`
(`--skip` flag), guide + manual `up` sections, tests. Blueprint schema
unchanged.

**Decision (2026-08-29): plan 21 is the dedicated design record.** The plan
keeps the first implementation narrow: run the command once with the full
instance environment, before workloads; do not parse migration stdout; report
a count only when live `applied_migrations` metadata permits it; and retain
the existing rollback path for command failure. `--skip` is limited to
`migrate` and `verify`, with all names validated before side effects.

Plan 21 is [`docs/plans/21-up-migrate.md`](../21-up-migrate.md). `up` is the
most fragile surface in the codebase — rollback ordering, phase output, and
the base-vs-instance env-plumbing trap above all deserve the edge-case
discipline before touching it. The plan is sequenced before #76 because both
features modify `up`.

### Phase 2 — Agent-facing: #76 (work records) — P2, design-first

**Issue:** #76 — a durable text file per instance carrying intent and
verdict.

The rationale is the strongest part: the throughput ceiling is review, not
compute, and "what was this instance supposed to do, and did it do it" is
currently reconstructed manually from branch, transcript, and memory. Intent
is useful whether supplied by a human or an external AI operator; it records
the task the operator is asking the instance to perform. Records in the
registry directory survive `down`, which is the right home: the worktree dies
on purpose.

Scope check — stays on-mission:

- No daemon, no scheduling, no orchestration. A file per instance,
  create-don't-collide, append-only by convention (same social guarantee
  as the mailbox — plax cannot and should not enforce it against an agent
  with filesystem access).
- Intent is supplied through the CLI at `up` time (`--parent`, `--intent
  <file>`), not generated by a model; no model is in the path.
- The surface is four commands (`up` flags, `plax log`, `plax record`,
  `plax verdict`), with records-to-stdout / chatter-to-stderr and `--json`
  on `record`.

**The format-substrate bet is honestly stated in the issue itself** ("a
format only this repo uses is a good personal workflow, not a substrate")
— worth building on its own merits, but the ambition should be recorded,
not assumed. Nothing in the proposal depends on a second tool agreeing
today.

**Relationship to open question 3** (`docs/design.md` §7 L479): the issue
claims records close it, arguing message and record want the same RFC-822
envelope. Accept the envelope idiom for *records*; keep open question 3
open for agent-to-agent *messaging* — different retention, different
producer, and no second tool has spoken yet. The argument is plausible,
not settled.

**Decision (2026-08-29): plan 22 is the dedicated design record.** The
strongest concrete use of `--parent` is stacked work: an instance child is
branched from its parent's exact current worktree `HEAD`, while the record
keeps the lineage. This is a snapshot relationship, not live tracking; an
external operator running from the main repository has no implicit parent
and creates a root with `--intent`. The plan deliberately combines Git
ancestry and record lineage for v1 rather than inventing a second task-parent
graph. It also requires `--intent` for a tracked child, since the issue's
inheritance mechanics were underspecified and self-authored intent is valid
operator input after all.

Plan 22 is [`docs/plans/22-work-records.md`](../22-work-records.md). It is
sequenced after Phase 1 because both #75 and #76 touch `up`; the plan is
ready for implementation once the migrate phase lands. The plan also records
the current boundary that `contract` is stored and projected but is not yet
an executable extension to the fixed-check `verify` command.
